# ToonTest_01 — v6j: 속눈썹 끝 수정과 Unity 런타임 드라이버 (2026-11-13)

`MG_ToonTest_01_v6i.blend` 를 열어 만든 `MG_ToonTest_01_v6j.blend` 이다. 프로젝트에는 반영하지 않았다.

보존한 원본: v6f_A(15:07), v6i(10:42), v6g_s, v6h.

손대지 않은 것: 헤어 v5g, 아이템 시스템, 기존 캐릭터·프리팹·씬, Cubism, PSD, DB, 패키지.

Unity 에 새로 만든 것은 실험 폴더뿐이다: `Assets/_Experiments/ToonTest_01/Runtime/` (asmdef `MMG.Experiments.EyeView`), `MG_ToonTest_01_v6j_eye.fbx`.

## 1. 속눈썹 끝

**원인:**
- v6i 의 보정 키는 속눈썹 띠를 Blink 경로로 내린다. 그래서 가닥도 아래로 돌아간다.
- 먼 쪽에서 보면 눈꼬리의 돌아간 가닥이 옆을 향해 가시처럼 갈라져 보였다.
- 광선으로 세어 보니 얼굴 실루엣 밖으로 나간 양은 오히려 A 보다 적었다. 문제는 실루엣이 아니라 눈 윤곽에서 떨어져 나온 가닥이었다.

**시도 1 (버림):** 가닥을 돌리지 않고 뿌리만 따라가게 했다. 가닥이 눈 중간 높이에서 옆으로 뻗어 나와 더 나빴다.

**채택 (`scripts/t81_eye_v6j_lash.py`, V6J_MODE=keep):**
- 보정 키(`ViewFar*`) 안에서만 바꿨다.
- 홍채 위에 있는 속눈썹 열은 v6i 처럼 눈꺼풀과 함께 내려온다.
- 홍채 바깥(홍채 반지름 0.85→1.2 배)의 열은 원래 자리로 서서히 돌아간다.
- 눈꼬리 플릭은 정면과 같은 모양으로 남고, 그 아래 흰자만 눈꺼풀 피부가 덮는다.
- 정면 r30 의 속눈썹 길이, 눈꼬리, 쌍꺼풀은 그대로다 (보정값 0).

얼굴 실루엣 밖 속눈썹 (광선 수, 0.5 px 간격):

| | A v6f_A | v6i | v6j |
|---|---|---|---|
| 35° 오른눈 | 220 | 42 | 75 |
| −35° 왼눈 | 133 | 38 | 86 |
| 45° 오른눈 | 237 | 158 | 132 |
| −45° 왼눈 | 351 | 90 | 169 |

v6j 는 모든 각도에서 A 보다 적다. 가시처럼 갈라진 가닥은 없어졌다 (`renders/compare_eye_v6j_lash_tail.png`).

## 2. Unity 런타임 드라이버 (`Runtime/EyeViewController.cs`)

- **유일한 작성 위치:** Blink, EyeSmile, Smile, Surprise, 시선(재질 `_GazeYaw`)과 보정 키 8개를 한 곳에서 최종 계산해 쓴다. LateUpdate 이고 실행 순서는 1000 (애니메이션 뒤)이다.
- **각도:** 눈마다 눈 위치에서 카메라로 가는 방향을 머리 공간으로 바꿔 yaw·pitch 를 구한다 (원근·직교 모두).
- **먼 눈 가중치:** 20°→40° 에서 0→1 이다. 60° 쪽 `ViewSide` 는 50°→65° 에서 0→0.8 이다. |pitch| 가 50°→75° 이면 보정이 꺼진다.
- **시선:** `_GO` / `_GI` 로 나눈다 (바깥 0.25, 안쪽 0.12 rad).
- **Blink·EyeSmile:** 모든 보정 키에 (1 − Blink)(1 − EyeSmile) 을 곱한다.
- **감쇠:** 선택 사항이다 (`smoothTime`). 한 프레임에 `cutDegrees` (20°) 이상 바뀌면 카메라 컷으로 보고 즉시 적용한다. 이번 테스트는 감쇠 없이 했다.
- **테스트 전용:** `EyeViewTestRig.cs` 는 테스트 시퀀스를 프레임마다 재생하고, 그 프레임의 정상 렌더 결과를 프레임 끝에 읽어 저장한다.
- **실행 방식:** `scripts/u12_unity_play_eye_v6j.cs` 가 플레이 모드에서 런타임 씬을 만들어 실행한다. 저장하는 것은 없다.

처음 버전은 LateUpdate 안에서 `camera.Render()` 를 직접 불렀다. 이 경우 BlendShape 스키닝이 한 프레임 늦게 반영돼 시퀀스 첫 프레임이 튀었다. 실제 게임 순서와 다르므로, 정상 렌더 루프 + 프레임 끝 캡처로 바꿔 다시 측정했다. 아래 수치는 다시 잰 값이다.

## 5. 성능과 메모리 (측정과 추정을 나눔)

**측정 (Unity 6000.6.8f1 Editor, Apple M5 Pro, gpuSkinning 켜짐, `scripts/u14_unity_cost_eye_v6j.cs`)**

| 항목 | A v6f_A | v6j | 차이 |
|---|---|---|---|
| BlendShape 수 | 31 | 47 | +16 |
| 눈꺼풀·속눈썹 메시 메모리 | 746 KB | 1,067 KB | +320 KB |
| 전체 메시 메모리 | 8,776 KB | 9,096 KB | +320 KB (+3.6 %) |
| 새 BlendShape 의 변화 정점 합계 | — | 7,725 | `ViewSide` 4개가 3,328 |
| 눈 메시 4개 BakeMesh, CPU 경로, 키 없음 | 35 µs | 40 µs | +5 µs |
| 같은 측정, 보정 키 켜짐 | — | 63 µs | |
| 같은 측정, Blink+EyeSmile+Surprise(+보정) | 80 µs | 94 µs | +14 µs |
| 컨트롤러 (플레이 모드) | — | 평균 14.3 µs | |

**추정 (기기 측정 아님)**

- **메모리:** 변화 정점 7,725 × 40 B (정점 번호 + 위치·노멀·탄젠트 차이) ≈ 300 KB 로, 측정값 320 KB 와 맞는다.
  - 메시 데이터는 같은 모델의 인스턴스끼리 공유된다. 그래서 캐릭터 종류당 +0.3 MB 이고, 인스턴스 수만큼 늘지 않는다.
  - 스키닝 출력 버퍼는 정점 수로 정해지므로 늘지 않는다.
- **CPU:** 모바일 CPU 를 M5 Pro 의 3~5배 느리다고 보면, 캐릭터당 프레임마다 컨트롤러 0.04~0.07 ms 다.
  - CPU 블렌드 경로를 쓰면 보정 키 적용에 +0.07~0.1 ms 가 더 든다.
  - GPU 스키닝을 쓰면 정점 수천 개 수준이라 GPU 부담은 무시할 만하다.
- **줄이는 방법:**
  - `ViewSide` 는 Blink 복사본이다. 각 눈 렌더러의 Blink 를 컨트롤러가 직접 올리면 4개(약 133 KB)를 없앨 수 있다.
  - 바뀐 값만 쓰거나 화면 밖 캐릭터를 건너뛰면 CPU 가 준다.

## 6. 남은 문제와 한계

- 가까운 원근 카메라에서는 눈마다 각도가 달라져, 같은 머리 각도에서도 보정이 더 강해진다. 기하적으로는 맞는 동작이지만 줌인 중에 먼 눈 모양이 천천히 바뀐다.
- 카메라를 위·아래로 25°·−20° 까지만 확인했다. 거의 수직인 시점은 pitch 감쇠 규칙에만 의존한다.
- 동시에 여러 카메라가 그리는 경우(분할 화면, 미러)와 컷 직후 감쇠 동작은 REPORT_16 6장과 같다. 이번에 감쇠는 끈 채로 시험했다.
- 안쪽 0.12 rad 를 넘는 시선에서는 바깥 흰자가 다시 보인다 (의도한 동작).
